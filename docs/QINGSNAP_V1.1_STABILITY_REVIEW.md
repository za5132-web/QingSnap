# QingSnap v1.1 稳定性审查报告

审查日期：2026-09-05
审查基线：QingSnap v1.0.2 工作树上的 v1.1 功能集
运行环境：Windows 64 位、.NET 8、双显示器（1920×1080 + 3840×2160）

## 结论

本轮没有增加产品功能，完成了代码审查、自动化回归、SQLite 压力测试、真实历史目录启动测试和一批稳定性修复。Release 全量编译为 **0 警告、0 错误**，自动化测试 **140/140 通过**。

当前建议定位为 **v1.1.0 Release Candidate**。第 17 步已经解决本报告中记录的“历史窗口最近 500 张”限制，详见《QingSnap v1.1 历史分页与缩略图优化报告》。在完成混合 DPI和多软件剪贴板人工测试后，可以发布 v1.1.0。未发现会损坏截图图片文件或旧配置的阻断问题。

## 已发现并修复的问题

| 风险 | 问题 | 修复 |
|---|---|---|
| 高 | 程序退出时，剪贴板 STA 线程尚未结束便释放队列，极端占用场景可能让后台线程异常退出 | 先结束入队并等待线程；只有线程确认退出后才释放队列 |
| 高 | 用户迁移历史目录后，同一图片的新路径可能丢失收藏、OCR、标签和来源信息 | 以图片哈希识别移动文件，先迁移完整 Metadata 和标签，再清理失效旧路径 |
| 中 | OCR 空闲释放可能与正在运行的识别竞争，提前释放本地 Engine | Engine 释放与识别共用互斥门，Dispose 等待活动识别结束并改为幂等 |
| 中 | 标注 Undo / Redo 快照无容量上限，超长标注会话可能持续占用内存 | 双栈保留最近 200 个操作；超限丢弃最旧快照，不改变撤销语义 |
| 中 | 历史目录设置在后台迁移过程中再次变化时，新迁移请求可能被忽略 | 迁移请求合并并循环处理，保证最后一次目录设置会执行 |
| 中 | SQLite 单批写入较小，10,000 条导入耗时偏高 | 批处理从 64 提升到 256，仍使用事务和参数化 SQL |
| 中 | Dispatcher 未处理异常记录后仍可能终止后台程序；未观察 Task 缺少统一日志 | Dispatcher 异常记录后标记已处理；接入 TaskScheduler 未观察异常日志并标记已观察 |
| 低 | 历史读取、OCR 结果窗、贴图/截图 OCR 预取部分异常只显示或静默忽略 | 补入现有 DiagnosticLog；取消操作仍按正常路径忽略 |

## 性能结果

### SQLite Metadata 压力测试

使用独立临时数据库、真实事务写入和全量读取；图片二进制不进入 SQLite。

| 条目数 | 写入 | 全量读取 | 托管内存增长 |
|---:|---:|---:|---:|
| 100 | 26.4 ms | 6.7 ms | 1.0 MB |
| 1,000 | 206.5 ms | 27.5 ms | 0.0 MB |
| 5,000 | 988.6 ms | 94.4 ms | 5.9 MB |
| 10,000 | 2,092.1 ms | 255.8 ms | 17.6 MB |

调整前 10,000 条写入约 4.24 秒，本轮约 2.09 秒，改善约 51%。

### 真实应用启动与资源

- 设置窗口：第一次约 2.28 秒，后两次约 1.40 / 1.42 秒。
- 设置窗口稳定后：工作集约 149 MB，私有内存约 68 MB，保持响应。
- 当前真实历史目录约 550 张；历史窗口冷启动约 1.38 秒。
- 历史窗口载入缩略图后：工作集约 200 MB，私有内存约 118 MB，保持响应。
- 最近范围截图蒙层启动与 Esc 返回完成冒烟测试，进程未退出、UI 保持响应。

上述数字为本机单次/小样本数据，不作为所有电脑的硬性承诺。

## 数据层与兼容性

- 普通模式数据库：`%LOCALAPPDATA%\QingSnap\history-metadata.db`
- 便携模式数据库：`QingSnap.exe` 同目录下 `Data\history-metadata.db`
- Schema 版本：1，保存在 `SchemaInfo`，为后续 migration 预留。
- 图片仍是历史目录内的普通 PNG / JPG / BMP 文件，数据库不保存图片二进制。
- 数据库损坏时会把损坏文件移开并重建，随后从图片目录恢复基础索引；图片本身不会删除。
- 旧版 `settings.json` 缺少新字段时使用安全默认值；旧收藏和 OCR 索引继续迁移。
- 用户手工删除图片后，刷新会清理失效 Metadata；删除数据库不会删除历史图片。

## 资源生命周期检查

- OCR Engine：串行化识别/释放，空闲释放和关闭不再与推理竞争。
- 长截图 Bitmap：完成输出后清理帧、段、固定区、滚动区和检查点缓冲。
- History Thumbnail：窗口使用回收虚拟化，但当前最多载入 500 张。
- Pin Window：关闭时停止定时器、取消并释放 OCR / QR CancellationTokenSource。
- Screenshot Overlay：关闭/取消时释放截图流程持有资源；OCR 预取异常有日志。
- SQLite：连接按操作 `await using` 释放；写队列批量事务化。
- Clipboard：专用 STA 队列关闭顺序已修复；截图保存不依赖剪贴板复制成功。

## 发布前仍需人工完成的测试

1. 在 100 / 125 / 150 / 175 / 200% DPI 逐一验证 F1、窗口识别、固定比例/尺寸、Alt/Shift、WASD、放大镜；再做主副屏交换、负坐标和跨屏切换。
2. 把全部标注工具各操作 20～30 分钟，重点观察多选、文字编辑、端点调整、滚轮合并、Undo / Redo 与内存是否回落到稳定区间。
3. 浏览器、文件列表、设置页、固定标题/底栏、大空白页面各做自动长截图；覆盖匹配失败转手动、Esc、Enter，并接近 80 屏 / 60,000px / 256MB 三个上限。
4. 真实验证 F3 最近五张、外部透明图片、多贴图、极大/极小缩放、M 收纳、左右边吸附、长图阅读、OCR 选字和 QR 热区；观察白闪、黑边、抖动与焦点。
5. 分别验证未安装 OCR、Tiny、Small、极速、节能、卸载重装和长图 OCR；确认 QR 在完全无 OCR 运行库时仍工作。
6. 使用隔离测试目录生成 10,000 张真实图片，检查历史窗口滚动、缩略图、搜索、多选、批量删除和重建；当前 500 张载入限制需先作产品决定。
7. 在微信、QQ、Chrome、Edge、Photoshop、Office、CAD 中复制/粘贴，并用剪贴板占用工具持续锁定剪贴板；确认复制失败时截图仍保存、稍后重试可恢复。
8. 使用任务管理器或性能分析器重复打开/关闭 OCR、长图、历史、贴图和蒙层至少 50 次，记录私有内存、句柄和 GDI 对象趋势。
9. 在 portable.flag 环境复制一份旧 v1.0.2 数据升级，验证配置、收藏、OCR 索引、标签、来源信息和图片文件均保留。
